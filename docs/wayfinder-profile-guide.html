New 2026.3 bundle

Configuration lives outside the bundle

Root profile.md, types.md, and actors.md registries are retired. The four named directory conventions and subject-based placement remain.

Existing 2026.2 bundle

Keep its declared contract

profile.md and types.md stay required; actors.md is required when actor-valued OKF fields are used. Migration is explicit, never automatic.

The four layers

Agent workflow

AGENTS.md

Tells agents where knowledge lives, which skills to use, and how to work in the repository. It is not a Profile declaration.

Reusable standard

Installed Profile

Owns normative bundle rules, eleven standard types, OKF compatibility, deterministic validation, and review guidance.

Project binding

wayfinder.json

Selects the exact Profile and bundle paths; adds project custom types, declared tags, and actor lookup metadata.

Concept data

Bundle frontmatter

Uses OKF fields for type, document lifecycle, provenance, sources, and explicitly applied tags.

Do not confuse these

A 2026.2 bundle’s profile.md is an ordinary concept containing a legacy selector. It is neither AGENTS.md nor the installed reusable Profile.

Project configuration

One named binding can serve more than one bundle. Each bundle explicitly selects its binding; configuration does not create new frontmatter fields or override Profile rules.

wayfinder.json · illustrative project binding
{
  "version": 1,
  "profiles": {
    "knowledge_profile": {
      "implements": "bitwild_profile/2026.3",
      "types": [
        {
          "name": "Source Document",
          "description": "An authoritative captured document."
        }
      ],
      "actors": {
        "claude-code/opus-5": {
          "name": "Claude Code"
        }
      },
      "tags": [
        {
          "name": "customer-reporting",
          "description": "Customer-facing reporting topic"
        }
      ]
    }
  },
  "bundles": [
    {
      "id": "knowledge",
      "path": "knowledge",
      "profile": "knowledge_profile"
    }
  ]
}

The shipped Profile manifest declares eleven standard types and no base tags. Project bindings declare the tags they actually use. The validator uses built-in Profile metadata checked for parity with that shipped manifest; it does not dynamically load arbitrary Profile JSON.

Profile sources and lockfile

The current 2026.3 runtime uses an installed Profile. This is the proposed design for retrieving Profiles from Git and reproducing the exact revision in CI; it is not current configuration syntax yet.

planned wayfinder.json · direct Profile source
{
  "version": 1,
  "profiles": {
    "bitwild_profile": {
      "source": {
        "git": "https://github.com/btwld/wayfinder",
        "ref": "v2026.3",
        "path": "profile"
      },
      "applies_to": ["./knowledge"]
    }
  }
}

ref accepts a branch, tag, or commit without a branch/, tag/, or commit/ prefix. path is the Profile directory inside that Git revision. The fetched manifest supplies the Profile release and must match the configured identity.

planned wayfinder.lock · resolved source
{
  "lock_version": 1,
  "configuration_sha256": "<canonical wayfinder.json hash>",
  "profiles": {
    "bitwild_profile": {
      "requested_ref": "v2026.3",
      "resolved_commit": "<commit>",
      "profile_release": "2026.3"
    }
  }
}

The lockfile records resolution metadata, not Profile rules, project vocabulary, knowledge content, credentials, or executable validator code. Formatting-only JSON edits do not invalidate it; semantic changes do. get refreshes declared references, upgrade deliberately moves branches or tags forward, and validation reports the corrective command instead of fetching silently.

Resolve

wayfinder get writes or refreshes the lock.

Upgrade

wayfinder upgrade requests the latest matching branch or tag revision.

Validate

wayfinder validate ./knowledge resolves when needed, then checks the configuration, lock, bundle files, and Profile rules.

Where knowledge goes

A durable concept lives with its subject, not in a folder named after its type or tag. The four fixed directory names remain architecture/, ways-of-working/, interactions/, and references/. Other subject names come from the actual project corpus.

Whole-bundle scope

wayfinder.json selects one binding for a whole bundle. It does not define a placement map, per-directory overrides, or nested Profiles. For interactions/ and references/, the Profile’s chronology/source organization rules still apply.

Tags and status

Field OKF 0.2 meaning Bitwild 2026.3 producer rule
status Optional document lifecycle value: draft, stable, or deprecated. Required explicitly, using the same three values. Never use it for priority, workflow, confidence, or how settled the subject is.
tags Optional topic strings; OKF has no central vocabulary. Each used tag must be declared by the Profile or binding. Duplicate declarations or uses, undeclared tags, and exact collisions with type, status, trust, or standard relationship labels fail.

Tag definitions are vocabulary, not automatic assignments. The installed 2026.3 Profile has no base tags; project bindings declare used topics such as customer-reporting. Whether a tag is truthful or merely a semantic alias requires Profile Review.

Captures, sharing, and defaults

Captures

captures/ is normally evidence beside the OKF bundle. Its intake files do not inherit the main bundle’s Profile or tags. If it becomes a separate OKF bundle, configure it explicitly.

Shared bindings

Several bundles may use one named binding when their custom types, tags, and actor lookup genuinely match. Otherwise use separate bindings.

Installed release

Install the same pinned Profile runtime on each machine. Committing wayfinder.json shares project configuration, not executable validator code.

Default bundle

default_bundle is reserved for future command selection. Current commands still take an explicit bundle path; there is no recursive bundle discovery or merging.

What validation checks

Wayfinder first preserves the independent OKF result, then applies deterministic rules for the selected release. Legacy 2026.2 keeps its own registry checks.

Area Automated validation Contextual Profile Review
Binding JSON shape, exact supported release, safe and unique bundle paths, referenced binding. Whether the selected binding reflects the project.
Types Standard and custom name collisions, used-type membership, index group order. Whether the type fits each concept’s meaning.
Actors Lookup shape and whether used actor IDs are declared. Whether identity, affiliation, role, and provenance are truthful.
Metadata Required fields, OKF field shapes, status values, unknown producer keys, declared/duplicate tags. Whether values are accurate and tags describe real topics.
Sources and links Source shape, ID and attribution joins, and deterministic link checks. Whether sources support claims and relationships have the intended meaning.
What PASS does not prove

Automated success does not establish subject placement, semantic accuracy, source credibility, or complete Profile conformance. Judgment Rules remain UNASSESSED until Profile Review.

Configured validation flow

  1. Parse and check wayfinder.json shape; resolve the listed bundle safely.
  2. Select the exact built-in Profile release and retain the independent OKF result.
  3. Validate type, tag, and actor registries against concept use and deterministic Profile rules.
  4. Report contextual rules separately as UNASSESSED.

Schema boundaries

Bindings cannot add arbitrary per-type frontmatter properties such as owner, priority, or confidence. OKF owns the frontmatter contract. A future type-specific constraint would require a reviewed Profile release and must use existing OKF fields, not turn wayfinder.json into a rules language.
