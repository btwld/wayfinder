Start here

Direct Profile sources keep reusable rules in a Profile package and put project paths and vocabulary in one wayfinder.json entry.

1

Declare the Profile

Add a Profile entry keyed by its identity, with a source and the bundle directories in applies_to.

2

Keep index.md and log.md. Add concepts under truthful subjects, using declared types and tags, then run wayfinder validate --fix to write okf's generated indexes.

Run wayfinder get once, then wayfinder validate ./knowledge. Validation reads the current lock and reports contextual Profile Review separately.

Direct source configuration

Configuration lives at the project root

wayfinder.json names the Profile source and applies it to bundle folders. There is no separate bundle registry or Profile alias layer.

Compatibility

Published 2026.2 remains supported

Existing 2026.2 bundles keep their in-bundle declarations until explicitly migrated. The unpublished version-1 bundles / implements draft is not a second configuration shape.

The four layers

Agent workflow

AGENTS.md

Tells agents where knowledge lives, which skills to use, and how to work in the repository. It is not a Profile declaration.

Reusable standard

Profile package

Owns normative bundle rules, standard types, OKF compatibility, deterministic validation, and review guidance.

Project selection

wayfinder.json

Names the source, applies it to bundle paths, and adds project types, declared tags, relationship names, and actor lookup metadata.

Concept data

Bundle frontmatter

Uses OKF fields for type, document lifecycle, provenance, sources, and explicitly applied tags, plus the Profile's one declared key, relationships.

Keep the layers separate

Agent guidance can explain how to work. The Profile defines the reusable contract. wayfinder.json selects and extends it for this project; it does not become a second rules language.

Project configuration

The profile key is the Profile identity. source locates the package, and applies_to lists the bundle directories that use it.

wayfinder.json · direct Profile source
{
  "version": 1,
  "profiles": {
    "bitwild_profile": {
      "source": {
        "git": "https://github.com/btwld/wayfinder",
        "ref": "main",
        "path": "profile"
      },
      "applies_to": ["./knowledge"],
      "tags": [
        {
          "name": "customer-reporting",
          "description": "Customer-facing reporting topic"
        }
      ]
    }
  }
}

ref accepts a branch, tag, or commit without a branch/, tag/, or commit/ prefix. The package manifest supplies the Profile release and must match bitwild_profile. The shipped Profile manifest declares twelve standard types, no base tags, and eleven standard relationship names.

One entry

A Profile entry can apply to several bundle folders.

Separate entries

Use another entry when a bundle needs a different Profile or vocabulary.

Explicit paths

Paths are relative to wayfinder.json and stay inside the project.

Sources and lockfile

Git sources resolve to exact commits. The lock records that resolution; older 2026.2 bundles keep their own declarations.

wayfinder.json · additive custom Profile
{
  "version": 1,
  "profiles": {
    "bitwild_profile": {
      "source": {
        "git": "https://github.com/btwld/wayfinder",
        "ref": "main",
        "path": "profile"
      },
      "applies_to": []
    },
    "client_profile": {
      "extends": "bitwild_profile",
      "source": {
        "git": "https://github.com/example/client-profile",
        "ref": "v1.0.0",
        "path": "profile"
      },
      "applies_to": ["./knowledge"]
    }
  }
}

extends is optional and independent of applies_to. A source-only parent may have an empty application list. A child inherits its parent's vocabulary and may add types, tags, relationship names, and actors. The chain must reach the installed Bitwild Profile; remote rule overrides are not executed.

wayfinder.lock · resolved source
{
  "lock_version": 1,
  "configuration_sha256": "<hash of canonical wayfinder.json>",
  "profiles": {
    "bitwild_profile": {
      "source": "https://github.com/btwld/wayfinder",
      "requested_ref": "main",
      "resolved_commit": "<commit>",
      "path": "profile",
      "profile_release": "2026.3"
    }
  }
}

Canonical hashing ignores formatting-only edits. Semantic changes to wayfinder.json make the lock stale. The lock records resolution metadata only; it contains no rules, project vocabulary, knowledge, credentials, or executable validator code.

Resolve

wayfinder get writes or refreshes the lock.

Upgrade

wayfinder upgrade advances a mutable branch or tag. A pinned commit does not move.

Read-only validation

validate reads a current lock/cache without fetching or writing; only --fix writes, and only okf's generated indexes. graph, index, and search do not resolve Profile sources.

Where knowledge goes

A durable concept lives with its subject, not in a folder named after its type or tag. The fixed directory names are architecture/, ways-of-working/, interactions/, references/, and the optional computations/, which OKF §10.4 names as the home for Attested Computation concepts. Other subject names come from the actual project corpus.

Profile scope

applies_to names the bundle directories that use a Profile. It does not define a placement map, per-directory rule overrides, or nested Profile selection. The Profile’s chronology and source-organization rules still apply inside each bundle.

Tags, status, and relationships

Field OKF 0.2 meaning Bitwild 2026.3 producer rule
status Optional document lifecycle value: draft, stable, or deprecated. Required explicitly, using the same three values. Never use it for priority, workflow, confidence, or how settled the subject is.
tags Optional topic strings; OKF has no central vocabulary. Each used tag must be declared by the Profile or project entry. Duplicate declarations or uses, undeclared tags, and exact collisions with type, status, trust, or relationship names fail.
relationships Not an OKF field; OKF §4.1 lets producers add keys, and generic readers keep them. The one key the Profile declares: a list of relationship and resource mappings. Each name must be declared by the Profile or project entry; it never goes in sources.

Tag definitions are vocabulary, not automatic assignments. Whether a tag is truthful or merely a semantic alias requires Profile Review.

Captures, sharing, and compatibility

Captures

captures/ is normally evidence beside the OKF bundle. Its intake files do not inherit the main bundle’s Profile or tags. Add it to applies_to only when it is intentionally a separate searchable bundle.

Share the source

Commit wayfinder.json and wayfinder.lock. Each machine resolves the same source into its local cache; credentials and fetched contents stay local.

2026.2 projects

The published 2026.2 in-bundle selector remains valid. A migration to 2026.3 is explicit work: add direct source and applies_to, resolve a lock, then migrate the bundle's root registries.

What validation checks

Wayfinder inspects OKF first, then reads the selected Profile source without fetching or writing. A source failure never reclassifies the independent OKF result.

Area Automated validation Contextual Profile Review
Configuration JSON shape, safe applies_to paths, source and lock state, manifest identity, and Profile release. Whether the selected Profile reflects the project.
Types Standard and project name collisions and used-type membership. Whether the type fits each concept’s meaning.
Actors Lookup shape and whether used actor IDs are declared. Whether identity, affiliation, role, and provenance are truthful.
Metadata Required fields, OKF field shapes, status values, undeclared producer keys, declared/duplicate tags. Whether values are accurate and tags describe real topics.
Sources and links Source shape, ID and attribution joins, relationship shape and names, and deterministic link checks. Whether sources support claims and relationships have the intended meaning.
What PASS does not prove

Automated success does not establish subject placement, semantic accuracy, source credibility, or complete Profile conformance. Judgment Rules remain UNASSESSED until Profile Review.

Configured validation flow

  1. Inspect the explicit bundle and retain its independent OKF result.
  2. For an OKF-conformant bundle, select a matching applies_to path and read its source chain from a current lock/cache.
  3. Check manifest identity and release, then validate types, tags, actors, and deterministic Profile rules.
  4. Report contextual rules separately as UNASSESSED.

Schema boundaries

Profile entries cannot add arbitrary per-type frontmatter properties such as owner, priority, or confidence. OKF owns the frontmatter contract. A future type-specific constraint requires a reviewed Profile release and existing OKF fields; wayfinder.json remains a selector and project vocabulary registry.
