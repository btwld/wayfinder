Wayfinder Profile and validation guide

This guide explains where rules, project configuration, agent instructions, and concept metadata belong—and what Wayfinder validates today.

The four layers

AGENTS.md

Repository workflow instructions: where knowledge lives, which skills to use, and how agents should work.

Installed Profile

Reusable normative rules, standard types, OKF compatibility, validator code, and review guidance.

wayfinder.json

Project-local binding: selected Profile, custom types, actor lookup metadata, bundles, and declared tags.

Bundle frontmatter

OKF concept data: type, lifecycle, provenance, sources, tags, and other upstream-defined fields.

Key distinction: profile.md in an existing 2026.2 bundle is an ordinary concept containing the legacy selector. It is not an AGENTS.md and it is not the reusable Profile definition.

Recommended project configuration

{
  "version": 1,
  "profiles": {
    "knowledge_profile": {
      "implements": "bitwild_profile/2026.3",
      "types": [
        {
          "name": "Source Document",
          "description": "An authoritative captured document."
        }
      ],
      "actors": {
        "claude-code/opus-5": {
          "name": "Claude Code"
        }
      },
      "tags": [
        {
          "name": "captures",
          "description": "Evidence-related topic"
        }
      ]
    }
  },
  "bundles": [
    {
      "id": "knowledge",
      "path": "knowledge",
      "profile": "knowledge_profile"
    }
  ]
}

The installed Profile owns standard types and rules. The binding adds only project custom types and lookup metadata. It cannot override Profile rules.

Tags and status

FieldOKF meaningProfile behavior
status Document lifecycle. Values are draft, stable, and deprecated. It is optional upstream. Requires the field explicitly and keeps the same values. It must not encode priority, workflow, confidence, or subject certainty.
tags Optional list of short topic strings. OKF does not define a central vocabulary. The next Bitwild binding declares the actual Profile and project tag vocabulary. Duplicate declarations, duplicate values within one concept, and reserved-value collisions are rejected.

A Profile declares tag definitions, and a project binding adds project definitions. The first Bitwild external-binding release should make this registry authoritative: an undeclared used tag is an error. Declared names must be unique and must not collide between the Profile and binding.

Captures, sharing, and defaults

Captures

captures/ is normally evidence beside the OKF bundle. Its intake files do not inherit the main Profile or tag registry.

Sharing

Several bundles may reference one named binding when their types, tags, and actors are intentionally shared.

Defaults

default_bundle is proposed. Current commands still require an explicit bundle path and do not discover directories.

If captures become a searchable OKF bundle, they receive a separate binding and are not silently merged into knowledge/. Installing the same pinned Profile package shares the reusable validator across machines; committing wayfinder.json shares the project binding.

Type-specific properties

The first design does not allow arbitrary per-type frontmatter properties such as owner, priority, or confidence. OKF owns the frontmatter contract, and the Profile currently does not define type-specific schemas.

If a future Profile needs a type-specific constraint, it must constrain existing OKF fields in a new Profile release. It must not turn wayfinder.json into a second frontmatter language.

Validation flow for the future binding

  1. Validate wayfinder.json shape.
  2. Resolve the bundle and Profile binding safely.
  3. Resolve the installed Profile and exact release.
  4. Run independent OKF validation.
  5. Merge Profile standard types with binding custom types.
  6. Validate type and actor references.
  7. Run deterministic Profile rules; report judgment rules as UNASSESSED.
Source documents: OKF 0.2, Concepta Profile 2026.2, the proposed Wayfinder schemas, and implementation guide §4.8. Existing 2026.2 bundles remain on their legacy profile.md, types.md, and conditional actors.md contract until migration.
